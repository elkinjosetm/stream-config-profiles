# Settle-mode recovery gated on host instance identity, not process existence

Settle mode recovers an orphaned session (`undo` never fired) outside of any streaming session, triggered at logon/unlock; the tempting guard — "the host process is still running, so do nothing" — is unsound because Vibepollo/Apollo runs as an always-on service, so its mere existence proves nothing about whether it's the same instance that owns the pending session recorded in `state.json` (it could have crashed and auto-restarted since). Settle instead compares the host process's `StartTime` against the pending session's `since` timestamp: no pending session → no-op; no matching host process → recover (nothing could be serving it); matching process(es) whose earliest `StartTime` is later than `since` → recover (it's a later instance, not the one that opened the session); an instance already running at or before `since` → no-op, it could still own the session; and any unreadable `StartTime` or unparseable `since` → conservative no-op, since the evidence is unreliable. "Recover" performs the same pending-recovery a `do` would, plus restores `_local` → disk and clears `state.json`. `since` is parsed with `RoundtripKind` and normalized before comparison, since `Process.StartTime` is always `Kind=Local` and comparing it against an unnormalized `Utc`-kind timestamp would silently misjudge every comparison. Accepted tradeoff: a genuinely stuck session (same host instance still running, client gone for good) is never recovered by settle — it waits for the next `do` or a host restart, a deliberately conservative failure mode.
