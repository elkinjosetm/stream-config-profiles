# In-place upgrade path with repointed elevation target

Re-running a newer `Setup.bat` (or `manager.ps1`) over an existing install silently changed nothing, because `Setup.bat` runs its extracted `%TEMP%\scp_<guid>\manager.ps1` directly without ever touching the installed PROGRAM copy — and if the GUI kept running from that throwaway copy, every subsequent elevation in the session would re-launch against a world-writable `%TEMP%` path instead of the installed one. `Show-ManagerGui` now calls `Invoke-ManagerAutoUpgrade` once, right before opening the Main Window (never before the First-Run Wizard, never from headless `-Action` dispatch): if the running script differs from `PROGRAM\manager.ps1`, `Update-ManagerInstallationInPlace` re-runs `Install-App` (idempotent — it refreshes PROGRAM and DATA's always-regenerated files while leaving paths/profiles/connection state untouched), rewrites (never creates) existing shortcuts best-effort, and writes PROGRAM *before* DATA deliberately — an interrupted upgrade this way always leaves the *next* launch running the new manager, which is what re-evaluates whether DATA still needs catching up. On success, all subsequent elevation for that GUI session is repointed to the freshly-written PROGRAM path.

## Consequences

`Test-ManagerUpgradeNeeded` compares file *contents*, not version numbers — running an older `Setup.bat`/`manager.ps1` against a newer install "upgrades" (silently downgrades) `manager.ps1`/`sync-configs.ps1`/`paths.example.txt` the same way it would upgrade them, with no guard against it; this is documented as a known caveat in install.md's "Updating" section rather than checked in code. Writing PROGRAM before DATA only makes a retry *possible*, not reliable: if PROGRAM succeeds and DATA then fails, both the upgrade-needed check and a re-run of the identical installer will see `Running == Installed` and skip, leaving DATA stale with no retry path the content/path check can detect — recovery needs a headless `-Action install` re-run or a newer build.
