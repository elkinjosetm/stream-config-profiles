# DPI awareness and adaptive GUI layout

Field reports against the WinForms manager GUI: blurry text on a 4K display (the process never declared DPI awareness, so Windows bitmap-stretched a 96-DPI-rendered UI) and cropped buttons at 150% DPI with a Main Window resize that only grew the paths list (fixed design-time control positions/sizes). `Enable-GuiDpiAwareness` declares per-monitor DPI awareness before any WinForms assembly loads or window is created — required, since Windows latches DPI awareness the first time it's consulted — via a P/Invoke fallback chain (per-monitor v2 → per-monitor v1 → system-DPI-only), each attempt independently try/caught so a missing DLL or no C# compiler never regresses below pre-fix behavior; this only runs on the GUI path, never the headless `-Action` dispatch that must keep working on non-Windows CI. Every form is created through a shared `New-GuiForm` factory with an explicit `Segoe UI 9pt` font and `AutoScaleMode = Font`, and the Main Window was rebuilt on a root `TableLayoutPanel` with `AutoSize` `FlowLayoutPanel` button rows so controls scale and resize instead of clipping (the wizard/connect-dialog screens keep their pixel-coordinate layout but gained the same font basis and `AutoSize` rows). `$form.MinimumSize` is deliberately computed *after* the auto-scale pass, from the layout's own `PreferredSize` — computing it first would double-apply DPI scaling — and is then clamped to the current monitor's `WorkingArea`, which can still shrink the window below its preferred size on an extreme DPI/small-desktop combination.
