# Watchdog runs entirely at user level; no boot-time task

The watchdog registers exactly two scheduled tasks — `...-Settle-Logon` (AtLogOn + session-unlock, enabled by default) and `...-Settle-Poll` (repetition interval, off by default) — both under an Interactive, user-level principal, never SYSTEM. An earlier build also registered a SYSTEM-level `...-Settle-Boot` task (AtStartup) to close the earliest post-reboot window, but it was removed: its action pointed at `<DATA>\sync-configs.ps1`, a file in the ordinary user's own writable data folder, so anything able to write there while the Boot task existed would get SYSTEM execution at the next restart — a real escalation surface for zero protection beyond what the Logon task's `AtLogOn` trigger (which fires at the same moment login happens) already provides. Separately, real Windows denies an *unelevated* `Register-ScheduledTask` call for any logon-type trigger even when the task's own principal is the calling user — a registration-time denial, not a runtime one — so a per-task `Success=$false` from `Register-Watchdog` is the GUI's cue (`Invoke-GuiElevatable`, at the `#region Gui` call sites) to offer a confirm-and-elevate retry; the headless `-Action register-watchdog` path just reports the failure. Because `-Force` re-registers unconditionally, this can prompt on every call that touches Logon, not just the first. `Register-Watchdog` is a full desired-state reconciler (registers what's requested, unregisters what isn't) rather than add-only, and `unregister-watchdog` also best-effort-removes a legacy Boot task for anyone who installed the interim build — that cleanup's own failure never fails the overall call, since deleting an admin-owned task from an unelevated process is expected to fail.
